# Finding GraphQL endpoints

Before you can test a GraphQL API, you need to first find its endpoint.

> As GraphQL APIs use the same endpoint for all requests.

> Burp Scanner can automatically test for GraphQL endpoints as part of its scans. It will raise a "GraphQL endpoint found" issue if any endpoints are discovered.

> This section explains how to probe for endpoints manually though.

## Universal queries

If you send a request with ` query{__typename}` to any GraphQL endpoint..

It will include the string `{"data": {"__typename": "query"}}` somewhere in the `response`.

This is known as a universal query and is a great tool for probing whether a URL corresponds to a GraphQL service.

The query works because every GraphQL endpoint has a reserved field called `__typename` that returns the queried object's type as a string.

## Common endpoint names 

When testing for GraphQL endpoints, you should look to send `universal queries` to...

```
/graphql
/api
/api/graphql
/graphql/api
/graphql/graphql
```

If these common endpoints don't work you could try adding a `/vl` to the front..

> GraphQL services will often responds to any non-GraphQL request with a 'query not present' or similar..


# Testing different request methods.

It is best practice for production GraphQL endpoints to only accept POST requests that have a content-type of `application/json`.

This it often done to protect against CSRF vulnerabilities.

Some endpoints may accept alternative methods, such as GET requests or POST requests that use a content-type of `x-www-form-urlencoded`.

If you can't find the GraphQL endpoint by sending POST requests to common endpoints, try resending the universal query using alternative HTTP methods (GET,PUT,POST,HEAD,OPTIONS,ect.)

# (After finding the endpoint) Initial testing

After finding the endpoint we can start testing.

If the endpoint is powering a website, we can try exploring the web interface in burp browser and use the HTTP history to examine the queries sent.

## Exploiting unsanitized arguments

We can start testing, testing query arguments is a good start.

If the API uses arguments to access objects directly, it may be vulnerable to access control vulnerabilities(AC).

A user could potentially access information they should not simply have by supplying an argument that corresponds to that information.

    - This is called IDOR (Insecure direct object reference)

### Example of IDOR in GraphQL

```
    #Example product query

    query {
        products {
            id
            name
            listed
        }
    }
```
```

    #Example product response

    {
        "data": {
            "products": [
                {
                    "id": 1,
                    "name": "Product 1",
                    "listed": true
                },
                {
                    "id": 2,
                    "name": "Product 2",
                    "listed": true
                },
                {
                    "id": 4,
                    "name": "Product 4",
                    "listed": true
                }
            ]
        }
    }
```

> Things we can infer...
    1.  Products are assigned a sequential ID.

    2.  Product ID 3 is missing from the list, possibly because it has been delisted

```
    #Query to get missing product

    query {
        product(id: 3) {
            id
            name
            listed
        }
    }
```
By quering the ID of the missing product we can get its details even though its not listed on the shop and was not returned by the original product query.
```
    #Missing product response

    {
        "data": {
            "product": {
            "id": 3,
            "name": "Product 3",
            "listed": no
            }
        }
    }
```

# Using the Schema

The best way to piece together information about the database schema is through `interspection` queries.

> Introspection is built into GraphQL(as a function) that enables you to query a server for information about the schema.

Benefits:

    1. Helps understand how you can interact with the GRAPHQL API
    2. It can disclose potentially sensitive data, such as description fields.


## Using Introspection

To use introspection, query the `__schema` field.

Like regular queries you can specify the fields and structure of the response you want to retrun when running an introspection query.

Eg: you might only want the response to contain names of availible mutations.


> Burp can generate introspection queries for you.(see Accessing GraphQL API schemas using introspection)

## Probing for introspection

> It is often BEST practice to *DISABLE* introspection in production environments, but this isn't always followed.
#
You can probe for introspection using..
```
    #Introspection probe request

    {
        "query": "{__schema{queryType{name}}}"
    }
```
#

> Again Burp Scanner can automatically test for introspection during its scans, If it finds that introspection is enabled, it reports a "GraphQL introspection enabled" issue

# Running a FULL introspection query

Run this to get the full schema brah

> If introspection is enabled but this doesn't work.. try removing `onOperation`, `onFragment`, and `onField` directives from the query structure.

Some endpoints don't accept these directives as part of the introspection query, you can often have more success with introspection by removing them.

> Try going to GRAPHQL VOYaGER website their introspection usually works...(CWES Experience)

```
    #Full introspection query

    query IntrospectionQuery {
        __schema {
            queryType {
                name
            }
            mutationType {
                name
            }
            subscriptionType {
                name
            }
            types {
             ...FullType
            }
            directives {
                name
                description
                args {
                    ...InputValue
            }
            onOperation  #Often needs to be deleted to run query
            onFragment   #Often needs to be deleted to run query
            onField      #Often needs to be deleted to run query
            }
        }
    }

    fragment FullType on __Type {
        kind
        name
        description
        fields(includeDeprecated: true) {
            name
            description
            args {
                ...InputValue
            }
            type {
                ...TypeRef
            }
            isDeprecated
            deprecationReason
        }
        inputFields {
            ...InputValue
        }
        interfaces {
            ...TypeRef
        }
        enumValues(includeDeprecated: true) {
            name
            description
            isDeprecated
            deprecationReason
        }
        possibleTypes {
            ...TypeRef
        }
    }

    fragment InputValue on __InputValue {
        name
        description
        type {
            ...TypeRef
        }
        defaultValue
    }

    fragment TypeRef on __Type {
        kind
        name
        ofType {
            kind
            name
            ofType {
                kind
                name
                ofType {
                    kind
                    name
                }
            }
        }
    }
```

It's hard to read through the responses at times.
Using a GRAPHQL visualizer helps alot like `GraphQL voyager` to see the relationships easier.

### Suggestions

Even if introspection is entirely disabled, you can sometimes use suggestions to glean information on an API's structure.

Suggestions are a feature of the Apollo GraphQL platform in which the server can suggest query amendments in error messages. These are generally used where a query is slightly incorrect but still recognizable (for example, There is no entry for 'productInfo'. Did you mean 'productInformation' instead?).

You can potentially glean useful information from this, as the response is effectively giving away valid parts of the schema.

TLDR: Graphql might give you error messages that can give you info on the schema by suggesting correct schema values.

#### Clairvoyance

Clairvoyance is a tool that uses suggestions to automatically recover all or part of a GraphQL schema, even when introspection is disabled.

> To prevent this in apollo server v4 and above you can disable suggestions using `hideSchemaDetailsFromClientErrors`

> Burp scanner can automatically test for suggestions as part of its scans, if active suggestions are found burp scanner reports a
"GraphQL suggestions enabled" issue.
